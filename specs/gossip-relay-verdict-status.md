|---|---|---|
| F-12 / O12 | Control events (peer / status / sync) can still drop. The backlog holds at most `BACKLOG_CAP` = 8,192 events, and status/sync payload events at most `BACKLOG_BYTES` = 64 MiB (`service/event_sink.rs::admit_backlog`); past either bound the event is dropped and counted (`doli_event_lane_shed_total{lane="backlog"}`, probe `channel control_dropped=`). | O12 (on overflow drop only re-derivable events) is NOT approved and undesigned. |
| INC-I-238 (G1) | An attestation signs only `(block_hash, slot)`: changing `height`, `attester_weight` or `bls_signature` of a member-signed attestation mints a new message id. Votes: JSON field order / whitespace variants. | Relay half CLOSED for attestations (M6, AUDIT-P1-506 residual): the verdict Accepts only a first-seen `(attester, slot)` or the first copy with a valid BLS half for that `(attester, slot)`, recorded in `AttestSeen` (never read from pool residency); ≤ 2 Accepts per `(attester, slot)`. Wire half OPEN (the signature still excludes those fields). Vote variants OPEN (AUDIT-P1-507). |
| F2-bucket | Attestations have their own per-peer bucket (20/s, burst 200; M5 decision C), so a vote or producer flood no longer starves them. No global attestation bucket and no BLS pairing cap yet. One forwarder that relays more than 100 attesters per 10 s slot can exceed the per-peer bucket (up to 2 forwards per `(attester, slot)` × attesters per 10 s slot vs 20/s; same 20/s as before M5). | Owed: global attestation bucket + BLS pairing cap (`rate_limit.rs`). |
| REQ-GRV-025 (audit F4) | The per-peer attestation bucket (20/s, burst 200: 200 attestations per 10 s slot on one link) goes into deficit when one forwarder relays more than ~100 producer-set members per slot. Since M6 a hop forwards up to 2 copies per `(attester, slot)` (first sight + first copy with a valid BLS half), so N members cost up to 2N per slot. Pending members count: the attestation verdict admits them. | OPEN, follow-up (part of F2-bucket). Re-size the bucket above ~100 members. Owed BEFORE any mainnet deploy: measure the live producer-set size, pending included, against the 100-member threshold. |
| M5-DEV-F1 | One member key could sign `(attester, slot)` for any future slot; each was first seen, so Accepted, forwarded and kept in `AttestSeen`. | CLOSED (M5 decision C): the swarm Ignores an attestation with slot > wall + 2 (`staleness.rs::ATTEST_FUTURE_SLOTS`). Risk: a relaying node whose clock lags ≥ 2 slots (20 s at 10 s slots) Ignores genuine current attestations. |
| G3 | The digest reply delta is a producer-topic publish to all peers, not a direct reply to the forwarder. | Owed: request-response reply. |
| AUDIT-P1-505 reach | M5 gave every zero-flow tx `Ignore`, so a genuine DelegateBond / RevokeDelegation / AddMaintainer / RemoveMaintainer reached only the origin's direct peers. | CLOSED (M8): admission refuses a forged one (signature or current-set multisig, as apply), so a genuine one relays multi-hop again; a zero-flow Registration stays never-forward. Residual: replay of a captured genuine tx (INC-I-246). |
| AUDIT-P1-509 | A captured genuine AddMaintainer / RemoveMaintainer could be rewritten without a key (`reason`, signature-entry order or padding, trailing bytes) into new txids, each admitted at fee 0 and forwarded. | CLOSED (M11): one resident per `(action, target)` (newness on the signed content), the apply precondition against the same current set (a mined change stops being a carrier when it applies), canonical bytes and no repeated signature entry; at most `MAX_MAINTAINERS` residents per action. Probe: `variant_forwards=0 middle_residents=1`. A front-run variant holds the slot with the same state effect (only `reason` may differ). |
| INC-I-246 | Delegation txs carry no nonce, expiry or chain binding, and apply does not check `RevokeDelegation.delegate`: a public past revoke can strip a later delegation; a mined DelegateBond can be replayed. | Admission stop-gap (M11, narrowed in M12.1): refuses a RevokeDelegation that names a delegate other than the effective one (current state + that delegator's queued updates in queue order), a DelegateBond apply refuses (received cap, mirrored), and a DelegateBond whose txid a canonical block carries (DelegateBond only since M12.2; checked after every other refusal; repeated copies hit a bounded cache; a side-block index entry does not refuse; no index entry admits). Block validity and apply are unchanged, so a producer can still mine a replay. OWED (consensus fix, activation height required): nonce / valid-before / chain binding in the signed preimage, and `RevokeDelegation.delegate == delegated_to` at apply. Residual until then: a mined revoke replays while D is again delegated to the same P (exempt from the mined check because a second honest revoke of the same delegate is byte-identical), and an honest re-delegation with the same `(D, P, bonds)` after a revoke is refused by the mined check. Since M12.2 a byte-identical old carrier of a REVERSED maintainer change is admissible again: the reverse change makes the old change take effect on the current set again, and no mined check covers maintainer changes (SEC-FIXVERIFY-R573-01, REQ-GRV-SEC-019; a keyless `reason` or order variant had the same reach before). A snap-synced node has no bodies below its snap height, so it admits an old mined DelegateBond (M12.2 FM7, unchanged from M11). Since M12.1 a revoke with no effective delegation and a DelegateBond that repeats the effective delegation are `MPTX016` (boundary standing). The honest edge flows refused until the fix ((a) same re-delegation `MPTX014`, (b) CLI revoke during a queued switch `MPTX013`, (c) dependent maintainer change at the set bounds `MPTX011`, (d) revoke then delegate back to back `MPTX016`, (e) a pending delegation holds the delegator's one slot) carry a cause and a workaround in `docs/error-codes.md` and `docs/rpc_reference.md` (REQ-GRV-039). |
| AUDIT-P1-515 | Admission proved possession of the delegator key, not standing: one keygen + one signature gave a fee-free DelegateBond / RevokeDelegation that every hop admitted and forwarded, and the boundary turned into a no-op. | CLOSED (M12.1): admission applies the boundary preconditions of `delegate_bonds_capped` / `revoke_delegation` on the applied ProducerSet plus the delegator's queued updates (`MPTX016`) and keeps one resident delegation tx per delegator. Probe: `middle_forwards=0 middle_residents=0` (100 / 100 before). Residual (FM2): another producer's same-epoch update (e.g. the delegate exits) can still turn an admitted tx into a no-op; looser direction only. A stale resident holds only its own delegator's slot (FM4). |
| AUDIT-P1-516 | M11 ran the mined check (one full canonical-block read) before every other check, on the event loop. A refused copy never became resident, so each copy paid the read again; one message could repeat a txid up to 2,000 times. | CLOSED (M12.2): the mined check runs last and only for a DelegateBond, outside every mempool lock; repeated copies hit a bounded cache (one height-index point get, no body read); one attempt per distinct tx per message. Probe: `body_reads=1` for 1,000 copies (1,000 before). Residuals: cycling more than 10,000 distinct mined DelegateBonds that pass every cheaper check re-pays one read each (FM3); the first copy after a restart pays one read (FM4); an old node still pays per copy (FM6). |
| M11 FM3 (corrected in M12.1) | The M11 commit states that a lagging snapshot refuses a tx apply would accept "for at most that block". That holds only for the in-flight block. A maintainer change that depends on a pending change at the set bounds gets `MPTX011` until that predecessor is mined, which can take more than one block. A lagging node can also refuse a delegation from a delegator registered in a block it has not applied (M12.1 FM3). Both refusals are `Ignore`, never a peer penalty. | Documented as edge flow (c) in `docs/error-codes.md` and `docs/rpc_reference.md`; no admission change until the INC-I-246 consensus fix. |
| F-15 | A transient `Ignore` can strand a valid chained or late received tx (no hop re-forwards it). Own-origin txs are covered by RPC Busy (R3). | Owed: O8 (origin re-publish of own unmined txs) or an RPC-visible status. |
| REQ-GRV-016 remainder | Not built: command-channel depth gauge, pending-verdict gauge, vendor `send_queue` drop metric (today counted inside the vendor handler and logged at WARN, not exported), 1/min INFO summary line. | Owed. |
| Block re-forward cliff (REL-573-R-01) | The M7.2 cap makes duplicate-cache retention min(300 s, 218,000 ÷ distinct-id ingress), not a fixed 180 s floor: 180 s holds only up to 1,211 ids/s, 12 slots (120 s) up to 1,816 ids/s, the 60 s block window up to 3,633 ids/s (120.8 s at the 1,804 ids/s soak ingress). The ingress is attacker-paced: a distinct-id flood on any topic (the vendor inserts the id before the topic check and before every DOLI bucket) evicts a genuine tip-block id oldest-first; when that block is sent again, an `AcceptBlock` with slot ≥ best skips the per-peer block bucket and is forwarded again (the global block bucket runs after the report and gates local delivery only). The cost is linear, not amplifying. Attestation newness (`AttestSeen`, M6) and tx newness (D5 txid residency, M5/M8/M11) do not depend on the cache. | OPEN, owed BEFORE any mainnet deploy: keep genuine block ids out of reach of a non-block flood (early return for unsubscribed topics before the vendor insert, a cache partition for block ids, or the per-peer block bucket on a non-first delivery of a known hash) and export an eviction counter. |
