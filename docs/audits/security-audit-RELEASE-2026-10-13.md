### Break-it attempts on the budget (task 1)
- **(i) Concurrency.** There is one `MinedCheck` per `Mempool` (`crates/mempool/src/pool.rs:228`, built at `:250` by `Default`). It is shared by `Arc` (`mined_check()`, `zero_flow_mined.rs:175-177`). RPC gets the node's own mempool (`bins/node/src/node/startup.rs:382-386`, `self.mempool.clone()`), so gossip, TxFetch and RPC all share one bucket. The bucket is a `std::sync::Mutex`, and the whole refill-and-spend runs under it. Two admissions cannot both take the last token. The receiver `self.budget()` (which takes the lock) is evaluated before the argument `Instant::now()`, so the clock is read inside the critical section and `at` never goes backwards. The scratch copy confirmed this: it logged `receiver(lock)` before `argument(Instant::now)`. In 200 trials of 16 threads racing a full bucket, no trial took more than the burst. The guard is a temporary in a plain `if` condition, so it is dropped before `carries` runs: the read never runs with the bucket lock held. The scratch program showed the same, because `try_lock` inside the branch body succeeded. Two concurrent admissions of the same not-yet-pinned txid can each spend a token. That stays inside the budget.
- **(ii) Clock and arithmetic.** The clock is `Instant` (monotonic). `saturating_duration_since` (`:48`) cannot panic, and a backwards `now` adds 0. `as_secs_f64` is finite, so `tokens` is never NaN or infinite. `.min(2.0)` saturates at the burst. Subtraction happens only when `tokens >= 1.0`, so the bucket never goes negative. A refused call still moves `at` forward but keeps the accrued refill, so honest time is not lost. I simulated the copied code with call intervals of 1 µs, 3 µs, 37 µs, 250 ms, 499.999 ms, 500 ms and 500.001 ms over 2-600 s. Every run stayed within `burst + 2/s × T` (for example 1,202 takes in 600 s against a bound of 1,202, and 11 in 5 s at 1 µs steps against 12), with tokens always in [0, 2]. A start 10 s in the future yields 2 takes, then refusals, with no panic. A 100-year idle period caps at 2 takes. Float rounding is at the 1e-16 level per add, which is negligible.
- **(iii) Other paths that force a decode at admission or in the gossip handler.** `admit_zero_flow` has three callers: `crates/rpc/src/methods/transaction.rs:220-230` (sendTransaction), `crates/rpc/src/methods/governance.rs:283-291` (submitMaintainerChange, which only ever builds Add/RemoveMaintainer at `:267-271` and so never reaches the DelegateBond-only gate at `zero_flow_mined.rs:191`), and `bins/node/src/node/validation_checks/mod.rs:999-1008` (`handle_new_transaction`). `handle_new_transaction` is reached from the 0xBA batch path (`event_loop.rs:308-310` → `handle_gossip_txs`) and from TxFetch responses (`network_events.rs:559-579`; 0xAA announcements reach it only through a fetch, and `on_tx_announcement` `:501-529` reads no block). The TxFetch path has no per-message dedupe, but it draws on the same cache and bucket, so it cannot bypass the budget. In the mempool crate, the only `get_block` is `zero_flow_mined.rs:125`. `snapshot_for` reads only the producer set and maintainer state (`zero_flow_auth.rs:39-64`). Non-DelegateBond types never enter `refuse_if_mined` (`:191`). The cache recheck is a point get (`:110`), not a decode. The only other block decodes in the node are the sync-request server (`validation_checks/mod.rs:1117-1131`) and the getTransaction RPC; both existed at the baseline and are outside admission (see Cross-Perspective Signals).
- **(iv) Cache poisoning.** `record` is called only at `:98`, after a real read finds the txid. MPTX017 returns at `:95`, before any `record`. A budget refusal therefore pins nothing (`m12_3_sec_020_budget_refusal_leaves_no_cache_entry`: no pin on refusal, then 1 read + MPTX014 + a pin after 600 ms). MPTX017 is an `Err`, so a refusal can never admit: the budget fails closed. A mined replay is never let through for lack of a token. `record` is now `pub(crate)` (`:132`), so no external crate can write a pin.
- **(v) Cross-peer starvation (D5).** See SEC-FIXVERIFY-R574-03 below. It is P3, not FAIL.
- **(vi) Shared bucket across gossip and RPC.** Each side can starve the other. sendTransaction is not an admin method (`crates/rpc/src/server.rs:31-43`, `:198-200`) and has no per-client rate limit in the rpc crate. An exposed RPC endpoint is therefore a drain source that the per-peer gossip bucket does not cover. It needs the same key-plus-corpus as the gossip route. The `[MPTX017] DelegateBond mined-check budget exhausted, retry` text (built by `zero_flow_policy.rs:83-88`, constant plus the `tx_type` Debug) leaks no secret. It tells the caller two things: the txid is in the tx index (getTransaction already says that) and the node's bucket is empty right now (a 1-bit oracle on other traffic). Both are negligible.

### SEC-FIXVERIFY-R574-03: one global body-read bucket lets a corpus holder delay a narrow honest flow — P3 — conf(0.70, observed path; honest-impact frequency inferred)
- **Classification:** INTRODUCED (M12.3; this is the D5 residual, documented in the M12.3 dev notes).
- **Location:** `crates/mempool/src/zero_flow_mined.rs:88-96`. The bucket is shared through `crates/mempool/src/pool.rs:228,250` and `bins/node/src/node/startup.rs:382-386`.
- **Vulnerability class:** CWE-400 / CWE-770 (a shared resource without per-origin fairness), limited to relay delay.
- **Data flow:** attacker peer (gossip 0xBA, ≤ 500 tx/s per peer, `crates/network/src/rate_limit.rs:158`) or RPC client → `handle_new_transaction` / `send_transaction` → `admit_zero_flow` → every cheaper check passes (registered, active, undelegated delegator D; valid signature; standing; newness) → `get_tx_block_height` hit → `get_hash_by_height` hit → `take` spends the refilled token → the read finds the txid → pin. The next corpus txid finds an empty bucket → MPTX017. An honest DelegateBond T whose txid is indexed at a height where the canonical block does not carry it also needs a token at `:94`. While the flood holds the bucket at about 0, T gets `[MPTX017]` on RPC and `Verdict::Ignore` on gossip (`gossip_txs.rs:21-27`), so this hop neither admits nor forwards it.
- **When an honest tx needs a token (evidence):** `put_block` writes `tx_index` for every stored block, side blocks included (`crates/storage/src/block_store/writes.rs:48-56`). `set_canonical_chain` (`writes.rs:107`) never touches `tx_index`: the only tx-index writes are `writes.rs:49,55`, and deletes happen only in maintenance (`delete_blocks_above`, `delete_block_by_height`, `prune_blocks_below`), which the reorg path does not call. A reorg re-validates the mempool but does not re-add the orphaned block's txs (`bins/node/src/node/block_handling.rs:1071-1080`). So an honest DelegateBond whose carrying block was orphaned stays indexed at that height. Its resubmission needs a token. `m11_tx_indexed_only_on_a_side_block_is_still_admitted` shows that it is admitted when a token is free. `m12_3_sec_020_index_hit_with_an_empty_bucket_reads_no_block_then_refills` and `m12_3_sec_020_send_transaction_with_an_empty_bucket_returns_mptx017` show that any index hit is refused with MPTX017 when the bucket is empty. Replays of already-mined txs (lagging peers) are refused either way (MPTX014 vs MPTX017), so nothing is lost there. Honest new delegations are never affected because their index lookup misses (`m12_3_sec_020_fresh_delegate_bond_admitted_with_an_empty_bucket`).
- **Attacker cost:** (1) a registered, active delegator key D. Its bond is collateral, not burned. D must be undelegated at replay time and the named delegates must be active. (2) More than `MINED_CACHE_CAP` = 10,000 distinct mined DelegateBonds signed by D. Each successful take pins one txid (FIFO), so a corpus C ≤ 10,000 drains only C tokens per node (about C/2 s) and then hits the cache. The corpus can be minted at the baseline: about 7,550 such txs fit in one 1.9 MB block per the probe setup, so this is about 2 blocks, or the attacker's own blocks. (3) A connection to each target node sending ≥ 2 index-hit txs/s, and about 50/s to win most refill races. That is far below the per-peer 500 tx/s bucket. Over RPC there is no rate cap.
- **Honest loss and recovery:** the loss is delay of a DelegateBond whose carrying block was orphaned (or that a stored side block re-indexed), and only at nodes the attacker floods. No funds, state or consensus are touched. Recovery: (a) a fresh-content DelegateBond (another `bond_count` or delegate) misses the index and is admitted at once with 0 budget. This option is not available for a 1-bond delegator re-delegating to the same delegate (docs flow (a)), who must AddBond first or wait. (b) A byte-identical retry: a token survives about 1/r s after each refill under a flood of r txs/s, so each attempt succeeds with probability about 1/r (inferred model; about 0.1% at r = 1,000/s, the per-node global gossip tx bucket, `rate_limit.rs:194`). With the flood stopped, a retry succeeds within 500 ms. (c) Any node that already holds T resident keeps it, because the residency check comes first (`validation_checks/mod.rs:983-988`, then `check_system_transaction`), and any producer holding T can mine it. For comparison: a flood at the global tx bucket rate already starves all gossip tx admission at a node, with no key needed (pre-existing; 200 tx/s at d0e15686). So the D5 residual is a narrow, low-rate variant of an existing starvation, not a new capability.
- **False positive check:** I looked for a per-origin share, an exemption for non-carrying hits, or a not-carried negative cache. None exists: `carries == false` returns `Ok(())` at `:101` without recording. The finding stands as a narrow residual.
- **Why P3 and not FAIL:** the D5 bar needs an honest loss that neither a retry nor another relay path recovers. Here (a) and (c) recover it at once and (b) recovers it with certainty after the flood. The precondition (an orphaned or side-indexed honest DelegateBond) is rare.
- **Remediation (optional, non-blocking):** remember a "not carried at (height, canonical hash)" result for a txid, so a side-indexed honest tx pays one read per node per cache lifetime. Or split the budget per origin class (RPC vs gossip, or per peer). Document the residual (SEC-FIXVERIFY-R574-04).
